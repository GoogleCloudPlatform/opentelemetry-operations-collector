# Tango-GBOC smoke test setup

`TestTangoSmoke` (`../tango_smoke_test.go`) installs the packaged
`otelcol-google` service on a GCE VM and appends
`--config=googlecontrolplane:xds://$TANGO_CP_ENDPOINT?gcp.fleet_id=$TANGO_FLEET_ID&region=$TANGO_REGION`
to the service's regular command line: through a systemd drop-in on Linux, and
by editing the service's `ImagePath` registry value on Windows. It then polls Cloud Monitoring until the
collector's self-o11y gauge `prometheus.googleapis.com/gcp.policy.set.active/gauge`
reports the pre-provisioned PolicySet (`gcp.policy.set.id`) at
`TANGO_EXPECTED_REVISION`. The gauge only changes after the collector has
applied (and ACKed) a revision received from the Control Plane, so that point
proves the Control Plane to Data Plane loop.

The test then checks that the two log filter policies are enforced. Because the
Control Plane does not yet translate source policies, the test replaces the
packaged `config.yaml` with a `filelog` receiver that mirrors the PolicySet's
`fileLogSourcePolicy` (same path on Linux, `C:\gboc-smoke\*.log` on Windows, no
parsing, so each line is a string body),
wired through the `googlepolicy` processor to the
`otlp_grpc/default_gcp_destination` exporter generated by the
`googlecontrolplane` config source. After the PolicySet is active, it uploads
[`sample_logs.log`](sample_logs.log), which holds one line that both filters
keep and one line for each filter to drop, then checks that only the kept line
reaches Cloud Logging.

The test assumes a long-lived fleet and PolicySet already exist and have been
rolled out. It never creates, updates or deletes them.

Current resources (project `stackdriver-test-143416`, number `228437877067`,
location `asia-east1`, staging Telemetry Management API, staging Telemetry
Director `staging-telemetrydirector.asia-east1.rep.sandbox.googleapis.com:443`):

| Resource | Name |
|---|---|
| Fleet | `projects/stackdriver-test-143416/locations/asia-east1/fleets/gboc-smoke-fleet` |
| PolicySet | `projects/228437877067/locations/asia-east1/policySets/gboc-smoke-ps` |
| Revision | `projects/228437877067/locations/asia-east1/policySets/gboc-smoke-ps/revisions/75cbca3b` |

The PolicySet body is in [`policyset.json`](policyset.json). It contains a
filelog source policy for `/var/log/gboc-smoke/*.log`, a log transform policy
and two log filter policies, all matching on the log body.
The Control Plane currently translates only `universalPolicies[].logFilterPolicy`
into the xDS `TelemetryCollector` resource, so the collector reports
`policies_loaded: 2`. The test relies on both filter policies.

## Recreating the resources

[`setup_policyset.sh`](setup_policyset.sh) performs the one-time project opt-in
and creates (or updates) the fleet and PolicySet, then rolls the latest revision
out to the fleet. It is not run by CI.

```
./setup_policyset.sh stackdriver-test-143416
```

A newly created fleet can take several minutes to become visible to Telemetry
Director. Until then the collector logs
`NotFound desc = Traffic Director configuration was not found`.

## Inspecting the resources

```
P=stackdriver-test-143416
BASE=https://staging-telemetrymanagement.sandbox.googleapis.com/v1alpha/projects/$P/locations/asia-east1
HDRS=(-H "Authorization: Bearer $(gcloud auth print-access-token)" -H "X-Goog-User-Project: $P" -H "X-Goog-Visibilities: TRUSTED_TESTER_COLLECTORS")

curl -sS "${HDRS[@]}" "$BASE/fleets/gboc-smoke-fleet"
curl -sS "${HDRS[@]}" "$BASE/policySets/gboc-smoke-ps"
curl -sS "${HDRS[@]}" "$BASE/policySets/gboc-smoke-ps/revisions/75cbca3b"
curl -sS "${HDRS[@]}" "$BASE/fleets/gboc-smoke-fleet/rollouts"
```

The `X-Goog-Visibilities` header is required. Without it the API answers
`404 Method not visible`.

## Running locally

The test needs a `.deb`/`.rpm` (Linux) or `.goo` (Windows) package of the
collector in GCS. Use a build that includes #768: the Control Plane now sends
the shared `Predicate` matcher proto, and older collectors NACK the filter
policies with `matcher must specify a valid predicate`.

```
cd integration_test/smoke_test
env PROJECT=stackdriver-test-143416 ZONES=asia-east1-a IMAGE_SPECS=debian-cloud:debian-12,windows-cloud:windows-2022 \
  KOKORO_BUILD_ID=local-$(date +%s) TRANSFERS_BUCKET=<bucket> \
  _BUILD_ARTIFACTS_PACKAGE_GCS=gs://<bucket>/<package-dir> \
  TANGO_CP_ENDPOINT=staging-telemetrydirector.asia-east1.rep.sandbox.googleapis.com:443 \
  TANGO_EXPECTED_REVISION=75cbca3b \
  go test -tags integration_test -run TestTangoSmoke -v -timeout 60m ./...
```

## Off-prem mode

`OFFPREM_MODE` makes the tests of this package run on a VM that resembles a
machine outside GCE. They are the same tests, with the same names:
`TestTangoSmoke`, and also `TestSmoke` (`../smoke_test.go`). There is no
separate off-prem test. Without `OFFPREM_MODE`, the tests do what the sections
above describe. The code of the mode is in `../offprem_mode_test.go`.

The mode is for manual runs for now. No CI job sets `OFFPREM_MODE`.

This work is based on the `gboc-experiment-policy` branch. The collector that
the `master` branch builds does not contain the Tango components, so
`TestTangoSmoke` cannot pass with it (see "Testing a local build").

In off-prem mode, a test treats each VM differently in two ways:

1. The collector is installed in three steps. First the VM downloads the
   collector package from `_BUILD_ARTIFACTS_PACKAGE_GCS`, while it still has
   `gcloud`. Then the test changes the VM as `OFFPREM_MODE` says
   (`gce.SimulateOffPrem`). Only then does the test install the collector,
   from the downloaded package.
2. From then on, the test uploads every file over ssh
   (`gce.UploadContentSSH`) instead of through GCS. For `TestTangoSmoke` these
   files are the collector config, the service drop-in and the sample logs.

These are the same in both modes: the machine type and the scopes of the VM,
what the test checks, and the Cloud Monitoring and Cloud Logging queries.

The name of a test does not show the mode. Two places do:

- The log directory of the test. `main_log.txt` names the mode in its first
  lines, and `simulate_off_prem.txt` holds what was done to the VM.
- The VM. In off-prem mode it is created with the label `offprem_mode`, whose
  value is the mode.

### Variables

`OFFPREM_MODE` selects what is changed on the VM. `guest-env` is the only
mode. With any other value, every test fails before it creates a VM.

In off-prem mode, a test fails before it creates a VM if any of these
variables are missing, and one message names all the missing ones:

- `_BUILD_ARTIFACTS_PACKAGE_GCS`;
- `KOKORO_BUILD_ID`, the id of the test run. For a local run, a value like
  `local-$(date +%s)` is sufficient;
- `TANGO_CP_ENDPOINT` and `TANGO_EXPECTED_REVISION`, for `TestTangoSmoke`
  only. Without `OFFPREM_MODE` the test is skipped when `TANGO_CP_ENDPOINT` is
  missing. In off-prem mode it fails: whoever sets `OFFPREM_MODE` asks for the
  test to run;
- `PROJECT` and `IMAGE_SPECS`.

`ZONES` is needed as for every test of this package. If it is missing, the
`gce` library says so and exits when the test binary starts, before any test
runs. `TANGO_FLEET_ID`, `TANGO_POLICY_SET_ID` and `TANGO_REGION` have the same
defaults in both modes. `TRANSFERS_BUCKET` is not used in off-prem mode: after
the package download, nothing goes through GCS.

### What `guest-env` does and does not prove

Before the collector is installed, `guest-env` removes the Google guest
environment from the VM: it stops and masks the `google*` systemd units, and
removes every installed `google-*` and `gce-*` package (the guest agent, OS
Login, the OS Config agent, the GCE configuration and disk expansion packages,
the Google Cloud CLI) along with the package repositories they come from. The
metadata server stays reachable and the VM keeps its service account.

A test that passes in this mode therefore shows that:

- the package installs, and the service starts, on a host that has neither the
  guest environment nor `gcloud`;
- on such a host the collector does what the test checks. For
  `TestTangoSmoke`: the collector receives the PolicySet from the Control
  Plane, reports it, and enforces its log filters on the way to the Data
  Plane;
- the test needs nothing of the guest environment once it is removed: from
  then on it reaches the VM over ssh only.

It does not show:

- how the collector behaves without a metadata server. The collector still
  authenticates as the VM's service account, resource detection still finds a
  GCE instance (which is why the log queries can be scoped to the instance),
  and the project of the xDS subscription still comes from the metadata server;
- that any other kind of credentials works;
- how the package gets onto a host without `gcloud`: the file is downloaded
  before `gcloud` is removed.

### Supported hosts and projects

Only Debian 12 (`debian-cloud:debian-12`) has been verified, so set
`IMAGE_SPECS` to it in off-prem mode. It has been verified with
`TestTangoSmoke` only: `TestSmoke` has not been run in off-prem mode yet. Not
supported:

- RPM-based Linux and Windows: removing the guest environment is not
  implemented for them yet. For such an image spec the test fails with the
  "not supported yet" error of `gce.SimulateOffPrem`. It fails for that image
  only, and only once the VM exists and its package is downloaded. If the GCS
  directory has no package for the image, the test fails at the download
  instead.
- Ubuntu: it takes the same path as Debian and has not been tried. The removal
  covers dpkg packages only, not snaps, which is how some Ubuntu images ship
  `gcloud`.
- Projects that enforce OS Login. This holds for every test of this package,
  in both modes: the tests log in with an SSH key that they put into the
  instance metadata, and they turn OS Login off for the VM, which such a
  project does not allow.

### Testing a local build

1. Build the package. At the root of the repository:

   ```
   make package-linux-amd64
   ```

   This builds the working tree for linux/amd64 only, and leaves an unsigned
   snapshot `.deb` and `.rpm` in `google-built-opentelemetry-collector/dist/`.
   The first run also downloads Go and builds goreleaser, as the Makefile of
   the distribution does. `DISTRIBUTION=<directory>` selects another
   distribution.

   The target first generates the collector sources from
   `google-built-opentelemetry-collector/manifest.yaml`, as the
   `goreleaser-release` target of the distribution does. This rewrites the
   sources that are checked in under `generated_collector/`, so those files
   change if they differ from what is generated. The manifest has to contain
   the Tango components: it has to list `googlecontrolplaneprovider` under
   `providers`. A collector built without them stops with
   `unsupported scheme on URI "googlecontrolplane:..."`.

2. Copy the package to a GCS directory that you own and that the service
   account of the test VMs can read. The test installs every package for the
   VM's architecture that it finds there, so keep one build per directory:

   ```
   gcloud storage cp google-built-opentelemetry-collector/dist/*.deb gs://<bucket>/<package-dir>/
   ```

3. Run the test in off-prem mode. This is a usual run of `TestTangoSmoke`,
   with `OFFPREM_MODE` set and with one image:

   ```
   cd integration_test/smoke_test
   env PROJECT=stackdriver-test-143416 ZONES=us-central1-a IMAGE_SPECS=debian-cloud:debian-12 \
     KOKORO_BUILD_ID=local-$(date +%s) OFFPREM_MODE=guest-env \
     _BUILD_ARTIFACTS_PACKAGE_GCS=gs://<bucket>/<package-dir> \
     TANGO_CP_ENDPOINT=staging-telemetrydirector.asia-east1.rep.sandbox.googleapis.com:443 \
     TANGO_EXPECTED_REVISION=75cbca3b \
     go test -tags integration_test -run TestTangoSmoke -v -timeout 60m ./...
   ```

   To run the same test on a VM that keeps its guest environment, leave out
   `OFFPREM_MODE`. The test then uploads its files through `TRANSFERS_BUCKET`
   again (see "Running locally").

   Without `-run`, `TestSmoke` runs too, in the same mode. It also needs
   `OTELCOL_CONFIGS_DIR`.
